我建议把 OJOS 设计成 **Kernel + Capability Modules + Extension Adapters**，不要把“赛制”“题型”“榜单”“发气球”“打印”“帖子”全部塞进一个 contest 服务里。否则后面每加一种比赛或题型都会互相改代码，模块化会失败。

核心思想是：

```text
Kernel 只管身份、模块、权限、事件、配置、路由、存储。
题型、赛制、榜单、评测、气球、打印、帖子都是可插拔能力。
```

---

# 一、总体分层

建议拆成 5 层。

```text
1. Platform Kernel
2. Domain Core Modules
3. Capability Modules
4. Adapter Modules
5. Launcher / Module Registry
```

对应关系：

```text
Platform Kernel
    ↓
Auth / Permission / Module Registry / Event Bus / Gateway
    ↓
Problem Core / Judge Core / Contest Core / User Core
    ↓
Scoring / Problem Type / Scoreboard / Operations / Community
    ↓
ICPC Tools Adapter / Polygon Adapter / Export Adapter
    ↓
Launcher 可视化安装与启停模块
```

---

# 二、Kernel 层：平台内核

这层必须非常稳定，不能经常因为业务变动而改。

## 1. auth

你现在已经有了。

职责：

```text
用户注册
登录
JWT
角色
用户身份
```

后续扩展：

```text
refresh token
token revoke
OAuth
第三方登录
```

---

## 2. permission

不要只靠简单 role。后面你会有：

```text
管理员
出题人
验题人
比赛管理员
气球志愿者
打印管理员
榜单操作员
普通参赛者
旁观者
```

建议做成：

```text
RBAC + Resource Scope + Capability Permission
```

也就是权限不只是：

```text
admin
user
```

而是：

```text
contest.manage
contest.balloon.send
contest.print.approve
problem.edit
problem.data.upload
submission.view.all
scoreboard.freeze
scoreboard.roll
module.install
```

并且带作用域：

```text
system
group
contest
problem
team
```

例如：

```text
user A 在 contest 3 中拥有 contest.balloon.send
user B 在 problem 7 中拥有 problem.edit
```

---

## 3. module-registry

这是你想要“PR 新模块，不改其他模块就能用”的关键。

要有一张模块注册表：

```text
modules
module_dependencies
module_capabilities
module_routes
module_permissions
module_feature_flags
```

每个模块提供一个：

```text
ojos.module.yaml
```

平台安装器读取它。

---

## 4. event-bus

继续用 NATS，但要分两类：

```text
普通事件：NATS Core
可靠任务：JetStream / DB Queue / Redis Stream
```

比如：

```text
user.registered                  普通事件
submission.created               可靠任务
judgement.finished               普通事件 + 可回放事件
balloon.requested                可靠任务
print.requested                  可靠任务
scoreboard.changed               普通事件
contest.frozen                   普通事件
```

---

## 5. gateway

Gateway 不应该知道具体模块逻辑。

它只应该做：

```text
配置驱动代理
统一鉴权
用户信息透传
限流
路由启停
```

后续模块安装时，Launcher 自动往 Gateway 配置里加：

```yaml
Proxy:
  Routes:
    - Prefix: /api/contest
      Target: http://contest-api:8083
      StripPrefix: /api
```

---

# 三、Domain Core：核心领域模块

这层是 OJ 的核心业务骨架。

---

## 1. problem-core

只负责题目元信息，不负责具体题型细节。

职责：

```text
题目基本信息
题面版本
标签
难度
来源
可见性
题目权限
题目归档
题目导入导出
```

核心表：

```text
problems
problem_versions
problem_statements
problem_tags
problem_permissions
```

不要在 problem-core 里写死：

```text
traditional
interactive
communication
output-only
```

这些应该由 `problem-type-*` 模块注册。

problem-core 只保存：

```text
problem_type = "traditional"
problem_type_config = jsonb
```

---

## 2. judge-core

judge-core 负责评测抽象，不负责具体语言，不负责具体题型全部逻辑。

职责：

```text
submission
judgement
testcase result
verdict
judge task
judge queue
```

它应该只理解：

```text
提交
评测任务
评测结果
测试点结果
```

不要让 judge-core 知道“ACM 罚时怎么算”“IOI 子任务怎么算”。那是 scoring 模块的事。

---

## 3. runner-core

你现在的 Rust judge-worker 后面应该演进成：

```text
judge-worker 调度器
runner-core 执行器
language-pack 语言配置
sandbox-provider 沙箱提供者
```

职责：

```text
编译
运行
限制资源
收集 stdout/stderr/time/memory/exit code
返回原始运行结果
```

这层不关心比赛、不关心排名。

---

## 4. contest-core

contest-core 只负责比赛实体。

职责：

```text
比赛创建
比赛时间
比赛题目列表
参赛队伍
参赛用户
封榜时间
可见性
比赛配置
比赛状态
```

不要把 ACM / IOI / NOI 的具体算分逻辑写死在 contest-core。

contest-core 应该保存：

```text
rule_module = "contest-rule-acm"
scoreboard_module = "scoreboard-icpc"
```

---

## 5. group/team-core

用于比赛组建。

职责：

```text
学校
组织
队伍
队员
教练
分组
账号批量生成
队伍报名
队伍审核
```

这个不要塞进 auth。auth 只管身份，team-core 管组织关系。

---

# 四、Capability Modules：能力模块

这层是可插拔能力。

---

# 1. 赛制模块 contest-rule-*

你要支持：

```text
OI
NOI
ACM / ICPC
IOI
启发式算法题
未来新赛制
```

不要写成 enum：

```go
ContestModeACM
ContestModeOI
```

否则以后加赛制还要改代码。

应该做成注册能力：

```text
capability: contest.rule
```

每个赛制模块实现统一接口：

```text
OnSubmissionJudged(event)
ComputeProblemScore(...)
ComputeTeamScore(...)
ComputeRanking(...)
GetFeedbackPolicy(...)
GetPenaltyPolicy(...)
GetFreezePolicy(...)
```

建议拆：

```text
contest-rule-acm
contest-rule-oi
contest-rule-ioi
contest-rule-noi
contest-rule-heuristic
```

---

## ACM / ICPC 赛制模块

负责：

```text
AC 题数
罚时
首次 AC
错误提交罚时
封榜
滚榜
气球触发
```

输出：

```text
team solved count
penalty
problem status
first to solve
```

---

## OI / NOI 赛制模块

负责：

```text
按测试点计分
按子任务计分
捆绑点
部分分
总分排名
```

支持：

```text
subtask
bundle
dependency
score aggregation
```

例如：

```text
subtask 1: test 1-5, min score
subtask 2: test 6-10, all-or-nothing
```

---

## IOI 赛制模块

IOI 和 OI 接近，但可以额外控制：

```text
赛时反馈策略
可见分数策略
提交次数策略
每题最好成绩
```

---

## 启发式算法题模块

这类题不要和普通 AC/WA 绑死。

需要支持：

```text
maximize
minimize
relative score
absolute score
best-known score
per-case score
排行榜按得分
多次提交取最好
```

例如：

```text
score = f(output, input)
normalized_score = user_score / best_score * full_score
```

这类模块应该依赖：

```text
checker / scorer
scoreboard
```

而不是普通 comparator。

---

# 2. 题型模块 problem-type-*

你要支持：

```text
传统题
交互题
通信题
提交答案题
```

建议拆成：

```text
problem-type-traditional
problem-type-interactive
problem-type-communication
problem-type-output-only
```

---

## traditional

传统题：

```text
input -> program -> output
checker 比较 output
```

依赖：

```text
runner-core
checker
dataset
```

---

## interactive

交互题：

```text
user program <-> interactor
```

需要：

```text
双进程通信
stdin/stdout 管道
交互协议
interactor 超时
用户程序超时
死锁检测
```

不要把 interactive 塞进普通 run_case。

---

## communication

通信题通常涉及多个程序：

```text
program A
program B
manager / grader
shared protocol
```

需要 runner 支持：

```text
多进程
多角色程序
通信管道
统一资源限制
```

建议独立模块，不要和 interactive 混在一起。

---

## output-only / 提交答案题

提交答案题不需要运行用户程序。

流程：

```text
用户上传答案文件
checker / scorer 检查答案
生成分数
```

这类题依赖：

```text
file storage
checker
scoring
```

不依赖 language-pack。

---

# 3. checker / scorer 模块

不要只有一种输出比较。

建议抽象成：

```text
checker.standard
checker.special
checker.float
checker.token
checker.output-only
scorer.heuristic
```

能力接口：

```text
Check(input, expected, actual) -> verdict / score / message
Score(input, output) -> score / details
```

传统题可以用：

```text
standard comparator
special judge
```

启发式题用：

```text
scorer
```

提交答案题用：

```text
output checker
```

---

# 4. dataset 模块

不要长期把测试点输入输出存在 PostgreSQL TEXT。

需要独立：

```text
dataset-core
```

职责：

```text
测试数据文件管理
测试点 metadata
子任务 metadata
捆绑点配置
样例数据
数据版本
数据权限
数据校验
```

存储结构可以是：

```text
data/problems/{problem_id}/{version}/tests/001.in
data/problems/{problem_id}/{version}/tests/001.out
```

数据库只存：

```text
testcase_id
problem_id
input_path
output_path
score
subtask_id
bundle_id
order
hash
```

---

# 5. scoreboard 模块

不要让 contest-rule 直接生成页面。赛制负责算结果，scoreboard 负责展示和导出。

建议：

```text
scoreboard-core
scoreboard-acm
scoreboard-oi
scoreboard-rolling
scoreboard-icpctools-adapter
```

能力：

```text
实时榜
封榜
滚榜
公开榜
管理员榜
队伍榜
学校榜
女队榜 / 特殊榜
导出榜单
```

---

## 滚榜 / 封榜

单独做：

```text
scoreboard-roll
```

职责：

```text
freeze
unfreeze
resolver
滚榜顺序
滚榜动画数据
reveal event
```

不要把滚榜写在 contest-core 里。

---

## ICPC Tools 兼容

单独做：

```text
adapter-icpctools
```

它的职责不是算榜，而是把 OJOS 内部数据转换为 ICPC Tools 需要的格式。

输入：

```text
contest
teams
organizations
problems
submissions
judgements
scoreboard events
```

输出：

```text
icpctools-compatible feed / package / files
```

这样以后内部模型改了，只需要改 adapter，不影响 contest-core。

# 五、模块可关闭机制

你说“支持把以上任意功能关闭”，这必须从一开始设计。

需要三层开关。

---

## 1. 模块级开关

```text
module enabled / disabled
```

例如：

```text
balloon-service disabled
print-service disabled
forum disabled
```

禁用后：

```text
不启动服务
不注册路由
不显示前端入口
不消费事件
```

---

## 2. 站点级功能开关

例如：

```text
site.features.balloon = false
site.features.print = false
site.features.forum = true
```

模块存在，但功能关闭。

---

## 3. 比赛级功能开关

例如某场比赛关闭打印：

```json
{
  "features": {
    "balloon": true,
    "print": false,
    "clarification": true,
    "public_scoreboard": true
  }
}
```

这样同一个系统可以支持不同比赛配置。

# 六、模块安装器 / 启动器设计

你要的“可视化安装任意模块”应该独立成：

```text
launcher
module-manager
```

---

## launcher 职责

```text
读取已安装模块
展示可安装模块
检查依赖
执行 migration
写入 module_registry
更新 gateway routes
生成 docker compose override
启动服务
注册前端入口
注册权限点
注册事件订阅
```

---

## 每个模块必须提供 manifest

例如：

```yaml
id: contest-rule-acm
name: ACM Contest Rule
version: 0.1.0
type: capability

requires:
  - id: contest-core
    version: ">=0.1.0"
  - id: judge-core
    version: ">=0.1.0"
  - id: scoreboard-core
    version: ">=0.1.0"

provides:
  capabilities:
    - contest.rule.acm

permissions:
  - contest.acm.configure
  - scoreboard.freeze
  - scoreboard.roll

events:
  subscribes:
    - judgement.finished
  publishes:
    - scoreboard.changed
    - balloon.requested

migrations:
  - migrations/000001_acm_rule.up.sql
  - migrations/000001_acm_rule.down.sql

routes:
  - prefix: /api/contest-acm
    target: http://contest-rule-acm:8091
    strip_prefix: /api

frontend:
  routes:
    - path: /admin/contests/:id/acm
      entry: frontend/admin-acm.js

features:
  - acm.penalty
  - acm.freeze
  - acm.first_to_solve
```

这样 PR 新模块时，核心系统只需要识别 manifest，不需要改已有模块。

# 七、模块之间如何通信

不要直接跨模块读表。

推荐顺序：

```text
1. 同步查询走 API
2. 状态变化走 Event
3. 大查询走 Read Model / Projection
4. 不允许随便跨模块改表
```

例如：

```text
judge-worker 评测结束
    ↓
publish judgement.finished
    ↓
contest-rule-acm 消费
    ↓
更新 contest_score_projection
    ↓
publish scoreboard.changed
    ↓
scoreboard-service 刷新榜单
    ↓
balloon-service 判断是否发气球
```

# 十三、推荐开发路线

不要一次写完所有。建议按这个顺序。

## Phase 1：模块内核


# 十四、几个关键决策

## 1. 不要把赛制写成 enum

错误：

```go
type ContestMode int
const ACM ContestMode = 1
```

正确：

```text
contest.rule.acm 是一个 capability
```

---

## 2. 不要把题型写死在 judge-worker

错误：

```rust
if problem_type == "interactive" { ... }
```

正确：

```text
problem-type-interactive 提供 execution plan
runner-core 执行 execution plan
```

---

## 3. 不要让 Gateway 知道模块逻辑

Gateway 只看：

```text
route prefix
target
auth required
rate limit
```

---

## 4. 不要让 shared 放业务配置

shared 只提供基础设施能力。

业务配置属于模块自己。

---

## 5. 不要跨模块直接改表

跨模块状态变化用事件。

---

# 十五、我建议你的核心架构名

可以正式定义为：

```text
OJOS Kernel + Module Capability System
```

一句话描述：

```text
OJOS 以 Kernel 提供统一身份、权限、事件、配置、路由与模块注册能力；
以 Capability Module 提供题型、赛制、评测、榜单、运营、社区等可插拔功能；
以 Adapter Module 兼容外部系统和格式。
```

这个方向能满足你提的要求：

```text
OI / NOI / ACM / IOI / 启发式算法题 ✅
未来新赛制 ✅
子任务 / 捆绑点 ✅
交互题 / 通信题 / 传统题 / 提交答案题 ✅
滚榜封榜 ✅
ICPC Tools 兼容 ✅
发气球 / 打印代码 / 小票 ✅
比赛组建 ✅
题库 ✅
分级权限 ✅
帖子 ✅
任意功能关闭 ✅
启动器可视化安装模块 ✅
PR 新模块不改旧模块 ✅
```

最先该做的不是继续写某个具体比赛功能，而是：

```text
module-registry + permission-core + feature-flag-core
```

这三个做完，后面的模块化才不会变成口号。

# 架构重构执行计划

本计划以 `0f70120` 为起点。它描述正在推进的改造，不代表目标边界已经全部实现。当前结构以[架构总览](README.md)和源码为准；契约入口见[服务契约与生成关系](service-authoring.md)。

## 不改变的产品约束

- 保留 Desktop、远程控制面、独立 Node Agent、OJ 业务服务和现有数据。
- 保留现有 HTTP/序列化契约、鉴权、幂等、事务、租约和补偿语义。需要改变行为时另列变更和迁移说明。
- 只在 `main` 提交，不重写历史。文档、协议迁移、用例迁移和行为修复分别提交。
- 软件验证代码、夹具、脚本和报告全部在仓库外；workflow 只承担产品构建、打包和发布。
- 以当前源码的外部验证、依赖关系和产品构建作为验收依据。编译成功不等于生产功能验收完成。

## 阶段与验收

| 阶段 | 交付范围 | 验收条件 | 状态 |

## 第一批范围与状态

A、B 和 C1 已完成，产品代码提交为 `8daef84`，已通过仓库外回归和对应提交的远端产品构建。C2 的 Release 校验仍引用安装规划的共同规则，不能只把函数搬到另一个文件后宣称完成分层。第一批没有修改安装、升级回滚、拓扑应用和数据库迁移。

协议迁移先覆盖运行时 profile、health policy、实例/观测、Node runtime report 和凭据刷新状态。其余执行 payload 与 Docker 适配的分离属于后续工作；不能把一部分协议提取等同于整个 runtime 已经解耦。

Catalog 的第一条纵向切片保留底层可信源校验和已部署视图的既有行为，通过明确读端口接入。旧 Console 若暂时仍作为视图适配来源，应留在适配层并标明，不允许用例反向依赖它。

## 下一批：C2 按用例推进

`backend/src/store_v1_api.rs` 的 `validate_release_catalog` 仍共同使用配置校验、组合规划、Node 能力、API Binding、Topology 和运行时 pipeline 规则。下一批按以下顺序拆解，每一步单独验收，不直接迁走整个文件：

| 顺序 | 工作与归属 | 必须保留的行为 |
| --- | --- | --- |
| C2a：纯规划规则 | 从配置/secret 引用校验、Release 文档转换、组合输入开始，把确定性规则放入 Store 应用模块；I/O 查询结果作为明确输入传入。HTTP 错误映射保留在适配层。 | JSON Schema 条件分支、secret 引用与明文的区别、稳定实例 ID、plan digest 的计算保持一致；不增加环境读取。 |
| C2b：只读校验用例 | 用只读端口取得可信 Release、Node facts、provider 和 Topology revision，再组合规划规则。HTTP 层只做输入解析、身份接入和响应映射。 | 区分 `valid: false` 和请求错误；保留签名/摘要验证、缺失依赖、runtime policy 与 Topology 确认要求；不导入 Release、不写 Operation/Job、不调用运行时。 |
| C2c：安装用例 | 复用校验与规划，明确“读取事实—确认计划—持久化并发布任务”的边界；底层事务由同一持久化适配器负责。 | 提交时重新检查 ETag、计划摘要与当前状态；保留幂等、并发协调、事务内记录以及任务入队/恢复语义，不能拆成彼此独立的写端口。 |
| C2d：替换与卸载 | 升级、回滚、卸载分别迁移；梳理历史 Release 证明、Binding generation、资源保留与补偿计划。 | 回滚仍要求可信历史 Operation；禁止更换已证明的 artifact；保留 generation、retained resource 和失败恢复规则。 |

这里的模块名和接口需由每条用例的实际输入决定，不先建一套空目录或通用框架。C2 完成后，Store HTTP 入口应能直接读出请求分派与契约映射，而不再承载配置计算、部署规划和事务编排。届时再收缩 `orchestrator-manager`/`orchestrator-legacy` 的导出；全仓路径改名仍留到 F。

## 每批交付规则

1. 明确本批输入、输出、依赖和不变量，再修改实现。
2. 先做保持行为的迁移；发现行为缺陷时单独记录和修复，避免混入机械移动。
3. 仓库外检查协议兼容、相关用例和依赖边界；对新源码副本运行既有回归。不能把旧实现覆盖回来后报告通过。
4. 构建受影响产品，检查 Git 差异和产品仓库边界，再提交。
5. 推送后核对对应提交的构建结果。只有验收完成，才把该阶段状态标为完成。

不以文件数、删除行数或统一命名作为主要成果。验收关注依赖方向、状态所有权、修改影响范围和明确的功能边界。

# 架构重构执行计划

本计划以 `0f70120` 为起点。本轮 A–F 的交付范围已完成，保留的技术债和未执行的真实服务集成验收在下文单独说明；完成本轮不代表整个系统已消除所有耦合。当前结构以[架构总览](README.md)和源码为准；契约入口见[服务契约与生成关系](service-authoring.md)。

## 不改变的产品约束

- 保留 Desktop、远程控制面、独立 Node Agent、OJ 业务服务和现有数据。
- 保留现有 HTTP/序列化契约、鉴权、幂等、事务、租约和补偿语义。需要改变行为时另列变更和迁移说明。
- 只在 `main` 提交，不重写历史。文档、协议迁移、用例迁移和行为修复分别提交。
- 软件验证代码、夹具、脚本和报告全部在仓库外；workflow 只承担产品构建、打包和发布。
- 以当前源码的外部验证、依赖关系和产品构建作为验收依据。编译成功不等于生产功能验收完成。

## 第一批范围与状态

A、B 和 C1 已完成，产品代码提交为 `8daef84`，已通过仓库外回归和对应提交的远端产品构建。C2 的 Release 校验仍引用安装规划的共同规则，不能只把函数搬到另一个文件后宣称完成分层。第一批没有修改安装、升级回滚、拓扑应用和数据库迁移。

协议迁移先覆盖运行时 profile、health policy、实例/观测、Node runtime report 和凭据刷新状态。其余执行 payload 与 Docker 适配的分离属于后续工作；不能把一部分协议提取等同于整个 runtime 已经解耦。

Catalog 的第一条纵向切片保留底层可信源校验和已部署视图的既有行为，通过明确读端口接入。旧 Console 若暂时仍作为视图适配来源，应留在适配层并标明，不允许用例反向依赖它。

## C2：已按用例完成的迁移

Release 校验、安装和替换共同使用配置、组合规划、Node 能力、API Binding、Topology 和运行时 pipeline 规则。C2 按以下顺序拆解，每一步分别验收：

| 顺序 | 工作与归属 | 必须保留的行为 |
| --- | --- | --- |
| C2a：纯规划规则 | 从配置/secret 引用校验、Release 文档转换、组合输入开始，把确定性规则放入 Store 应用模块；I/O 查询结果作为明确输入传入。HTTP 错误映射保留在适配层。 | JSON Schema 条件分支、secret 引用与明文的区别、稳定实例 ID、plan digest 的计算保持一致；不增加环境读取。 |
| C2b：只读校验用例 | 用只读端口取得可信 Release、Node facts、provider 和 Topology revision，再组合规划规则。HTTP 层只做输入解析、身份接入和响应映射。 | 区分 `valid: false` 和请求错误；保留签名/摘要验证、缺失依赖、runtime policy 与 Topology 确认要求；不导入 Release、不写 Operation/Job、不调用运行时。 |
| C2c：安装用例 | 复用校验与规划，明确“读取事实—确认计划—持久化并发布任务”的边界；底层事务由同一持久化适配器负责。 | 提交时重新检查 ETag、计划摘要与当前状态；保留幂等、并发协调、事务内记录以及任务入队/恢复语义，不能拆成彼此独立的写端口。 |
| C2d：替换与卸载 | 升级、回滚、卸载分别迁移；梳理历史 Release 证明、Binding generation、资源保留与补偿计划。 | 回滚仍要求可信历史 Operation；禁止更换已证明的 artifact；保留 generation、retained resource 和失败恢复规则。 |

这些模块名和接口由每条用例的实际输入决定。Store HTTP 入口现在负责请求分派与契约映射，配置计算、部署规划和提交协调已有各自入口。F 已让 backend 直接依赖 core 的纯规则，保留仍有调用方或迁移职责的兼容导出；没有为目录名一致而更改安装器和部署路径。

当前 C2a/b 的实现入口是 `manager/src/store/config.rs`、`composition.rs` 和 `validation.rs`：纯规则返回语义错误，HTTP 层负责状态映射；Release 校验通过只读端口取得事实与规划能力，不获得导入、提交事务、发布任务或执行容器的接口。C2c/d 已把宿主侧规划与 mutation 编排迁至 `backend/src/store`，校验适配器不再反向引用 HTTP 文件。`StoreAdmission` 统一协调锁、拓扑占用与失败撤销；Deployment 的真实卸载用例位于 `backend/src/deployment.rs`，Release 元数据删除仍是独立用例。具体边界与保留的限制见 [Store 与 Deployment](store.md)。

安装与替换仍是较复杂的宿主用例，暂时使用 Console 与 DurableStore，不宣称整个 manager/legacy 已解耦。D 已把后台协调和持久化适配器里的确定性 Binding 转换提取至 `core/src/binding_projection.rs`，并分开租约、恢复、探测、投影和 Job 应用。现有 SQLite/PostgreSQL 事务适配不变，规则由同一 core 实现提供；真实 PostgreSQL 集成验收仍需外部数据库。详见[后台协调](background-coordination.md)。

## E/F：客户端、服务入口与兼容引用

- 前端 API 已分为功能 client、响应适配和共用传输；旧 API 导出保持兼容。
- 控制面 Store 负责一致刷新，每个实例独立持有 Promise、取消句柄和定时器；展示投影是纯函数。旧布局响应先检查归属再更新状态；切换 Topology 前提交旧布局的待保存快照，保存结果按选择代次确认归属，避免旧请求污染新选择。
- Store 页面的安装、导入、部署变更与 Catalog 管理由各自表单持有状态。安装校验绑定请求时的输入、Catalog 来源与 channel，并在确认摘要完成后再次检查；过期结果不能授权当前参数。
- 前端正式调用方直接导入对应 feature；根目录旧文件只保留兼容导出。没有改变页面模板、样式和服务端 wire contract。
- 参考服务的 `main` 负责进程边界，`internal/app` 接收显式输入并组装组件；bootstrap 继续负责启动回滚和逆序关闭。v3 源输入、生成输出与 v2 分发/安装消费的边界已有明确说明。
- backend 的纯领域模型、动作/RBAC 元数据与规则直接来自 core；仍有业务用途的 Console、仓储和网络适配没有被盲目删除。

定位方式见 [Web 客户端](web-client.md)和[服务契约与启动](service-authoring.md)。本轮不把仍在使用的兼容实现或历史导入能力归为“失效代码”。后续深度迁移应单独处理旧 Console 的实际能力、其余 runtime 执行 payload，以及各 GoZero 服务的生命周期；这些属于保留的技术债，不是已经完成的改造。

## 每批交付规则

1. 明确本批输入、输出、依赖和不变量，再修改实现。
2. 先做保持行为的迁移；发现行为缺陷时单独记录和修复，避免混入机械移动。
3. 仓库外检查协议兼容、相关用例和依赖边界；对新源码副本运行既有回归。不能把旧实现覆盖回来后报告通过。
4. 构建受影响产品，检查 Git 差异和产品仓库边界，再提交。
5. 推送后核对对应提交的构建结果。只有验收完成，才把该阶段状态标为完成。
6. 阶段是验收节点，不是等待用户再次发起任务的节点；验收通过后继续后续阶段。只有需要改变产品行为、扩大授权范围或无法安全推进时才请求决定。

不以文件数、删除行数或统一命名作为主要成果。验收关注依赖方向、状态所有权、修改影响范围和明确的功能边界。

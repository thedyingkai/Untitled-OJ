# 架构重构执行计划

本计划以 `0f70120` 为起点。它描述正在推进的改造，不代表目标边界已经全部实现。当前结构以[架构总览](README.md)和源码为准；契约入口见[服务契约与生成关系](service-authoring.md)。

## 不改变的产品约束

- 保留 Desktop、远程控制面、独立 Node Agent、OJ 业务服务和现有数据。
- 保留现有 HTTP/序列化契约、鉴权、幂等、事务、租约和补偿语义。需要改变行为时另列变更和迁移说明。
- 只在 `main` 提交，不重写历史。文档、协议迁移、用例迁移和行为修复分别提交。
- 软件验证代码、夹具、脚本和报告全部在仓库外；workflow 只承担产品构建、打包和发布。
- 以当前源码的外部验证、依赖关系和产品构建作为验收依据。编译成功不等于生产功能验收完成。

## 阶段与验收

| 阶段 | 交付范围 | 验收条件 | 状态 |
| --- | --- | --- | --- |
| A：可信基线 | 当前/目标边界、契约所有权、文档矛盾、普通服务 OCI 构建 | 开发者能定位源输入、生成产物和兼容入口；产品构建不混入测试 | 已实现，等待远端构建验收 |
| B：共享协议 | 从 Agent/runtime 提取双方使用的纯协议类型，保留兼容导出 | 协议不依赖 HTTP、Docker、存储或 Agent；daemon 不再依赖 Agent crate；线上格式不变 | 已实现，等待远端构建验收 |
| C1：Catalog 只读切片 | 查询用例、读端口、HTTP 适配和已部署视图 | 用例不依赖 HTTP/Console/数据库实现；错误和分页行为保持一致 | 已实现，等待远端构建验收 |
| C2：Release 校验与 Store mutation | 先校验，再安装、升级回滚和卸载，逐用例迁移 | 保留签名、plan digest、ETag、事务与任务发布边界；无副作用校验仍无副作用 | 待开始 |
| D：后台协调和存储 | 拓扑协调、租约恢复、探测和投影分别归属；收敛仓储接口 | 领域转换与 I/O 分离；SQLite/PostgreSQL 保持相同业务语义 | 待开始 |
| E：客户端与服务开发 | 前端按功能分区，统一服务启动约定，理清 v2/v3 适配 | 状态、表单和接口位于对应功能；新服务不再猜测应编辑哪个契约 | 待开始 |
| F：目录和兼容层收尾 | 按已形成的职责改名、收缩导出、移除失效过渡层 | 文档和实际依赖图一致；旧数据的必要导入能力仍可用 | 待开始 |

## 本批范围

先完成 A、B 和 C1。C2 的 Release 校验仍引用安装规划的共同规则，不能只把函数搬到另一个文件后宣称完成分层。本批不修改安装、升级回滚、拓扑应用和数据库迁移。

协议迁移先覆盖运行时 profile、health policy、实例/观测、Node runtime report 和凭据刷新状态。其余执行 payload 与 Docker 适配的分离属于后续工作；不能把一部分协议提取等同于整个 runtime 已经解耦。

Catalog 的第一条纵向切片保留底层可信源校验和已部署视图的既有行为，通过明确读端口接入。旧 Console 若暂时仍作为视图适配来源，应留在适配层并标明，不允许用例反向依赖它。

## 每批交付规则

1. 明确本批输入、输出、依赖和不变量，再修改实现。
2. 先做保持行为的迁移；发现行为缺陷时单独记录和修复，避免混入机械移动。
3. 仓库外检查协议兼容、相关用例和依赖边界；对新源码副本运行既有回归。不能把旧实现覆盖回来后报告通过。
4. 构建受影响产品，检查 Git 差异和产品仓库边界，再提交。
5. 推送后核对对应提交的构建结果。只有验收完成，才把该阶段状态标为完成。

不以文件数、删除行数或统一命名作为主要成果。验收关注依赖方向、状态所有权、修改影响范围和明确的功能边界。
